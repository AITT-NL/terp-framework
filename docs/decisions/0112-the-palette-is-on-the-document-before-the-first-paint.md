# 0112 — The palette is on the document before the first paint

- **Status:** Accepted
- **Date:** 2026-09-04
- **Relates:** [ADR 0104](0104-the-spa-document-carries-its-own-security-headers.md) (the strict
  `script-src 'self'` this fix has to live inside — it is what rules out the inline snippet
  everyone reaches for first),
  [ADR 0094](0094-attribute-keyed-styling.md) (one stylesheet keyed on data
  attributes; the palette is one such attribute, and this ADR is about *when* it lands),
  [ADR 0100](0100-the-layout-declaration-is-one-document.md) (`defaultTheme` as a declared fact,
  which is the half of this that needs no script at all).

---

## Context

A person's theme is their own choice, so it is persisted in `localStorage` under `terp.theme` and
only script can read it. `ThemeProvider` reads it and applies it as `data-theme` on `<html>` in an
effect — the earliest moment React has committed anything.

That is too late, and the reason is structural rather than a matter of milliseconds. A Terp app is
a single-page app: `index.html` ships an empty `<div id="root">`, so there is nothing to lay out
until the bundle has been fetched, parsed and mounted. The browser paints before then. What it
paints from is the token sheet's `:root`, which is the **light** palette with
`color-scheme: light` — so a viewer who chose a dark palette got a white flash on every reload,
then the app they asked for.

Three properties of that defect are worth stating, because each one shaped the fix.

**It tracks an explicit choice, not a dark preference.** The token sheet carries
`@media (prefers-color-scheme: dark) :root:not([data-theme])`, which the browser resolves before
paint with no script at all. So the viewer who follows their platform has never flashed. The
viewer who *chose* dark — or midnight, or twilight — flashed every time, and so did an app that
ships on a dark palette through `defaultTheme`. That asymmetry is why the report reads as
intermittent.

**Development and production fail for two different reasons.** In a production build Vite extracts
the imported token sheet to a `<link>` in the head, so the palettes exist at first paint and the
attribute is the only thing missing. In a dev server the entry point *imports* `tokens.css`, so the
palette arrives with the bundle: the attribute alone fixes nothing there, because there is no
`[data-theme='dark']` block to match yet.

**There is no SSR here to turn off, and adding it would not be the fix.** The framework renders no
HTML on a server — `ssr.test.tsx` is a "renders without browser globals" smoke test over
`renderToString`, and nothing consumes it. A server could not read this value anyway: it is in
`localStorage` by design, so server rendering would first require moving the choice into a cookie.
A rendering architecture is not the answer to one paint.

## Decision

**Every generated app serves a blocking, same-origin classic script that puts the palette on the
document before the first paint.** It ships as `frontend/public/theme-bootstrap.js` and is wired
into `index.html`, both from the template; the example app carries a byte-identical copy as the
reference.

Each adjective is a constraint, and naming them is most of the decision:

- **Blocking** — no `defer`, no `async`, no `type="module"`. All three run the script after the
  document is parsed, which is on the far side of the paint this exists to beat. Putting the same
  code at the top of the module entry point has exactly the same problem, and looks tidier.
- **Same-origin, not inline.** Production serves `script-src 'self'` with no `'unsafe-inline'`
  (ADR 0104), while the dev server permits inline script because Vite's Fast Refresh preamble is
  one. So the usual inline `<script>` in `<head>` works in development and is silently refused in
  production — the exact dev/prod asymmetry ADR 0104's own dev mirror warns about. A CSP hash was
  the alternative and was declined: it puts a digest of a script into an nginx config, where it
  has to be regenerated by hand every time the script changes, and where getting it wrong fails
  closed and silently. A 200-byte cached file from the app's own origin costs one round trip and
  no maintenance.
- **Classic and untranspiled**, because `public/` is copied verbatim: this file is served as
  written, so it is small ES5 with no imports, no build step and no dependency on the bundle.
- **It declares the appearance as well as the palette** — but only when a palette is actually
  pinned. `color-scheme` is what the browser paints the canvas and the native scrollbars from,
  and declaring it is the half that fixes development, where the token sheet arrives with the
  bundle and the attribute alone has nothing to paint from. It is applied through CSSOM rather
  than a `style` attribute, which the same CSP would refuse. With no palette pinned the script
  declares nothing: the sheet's own `prefers-color-scheme` block answers that case before paint
  with no script at all, and an inline `light dark` written for a palette nobody chose would
  outlive its purpose in an app that composes `TerpProvider` without a `ThemeProvider` — OS-dark
  native chrome on a light app, from a bridge with nothing at the other end.

The script does the least it can: a stored `"system"` removes the attribute (so the sheet's
media query answers), a stored palette this build ships is stamped, and anything else — no
choice yet, or a name removed by an upgrade — leaves the document's own declaration standing.
`ThemeProvider` validates against the same list and reaches the same answer on mount.

**The inline `color-scheme` is a bridge, and `ThemeProvider` gives it back.** An inline value
outranks every rule in every layer, so keeping it would pin the native chrome to whatever was
stored at load: a viewer who then picks a light palette would keep dark scrollbars, a dark caret
and a dark `<select>` popup for the rest of the session, on a page that is no longer dark. The
effect that applies `data-theme` removes the property in the same pass.

**A declared default is declared TWICE, and both halves are load-bearing.** An app that ships
on a palette says so in `layout-contract.json`, which the bundle reads — and the bundle is what
is too late. So `terp guide theming` says to put the same name on the element as well
(`<html lang="en" data-theme="midnight">`), which needs no script at all, and the bootstrap
overrides it only for someone who has actually chosen otherwise. The attribute is not an
alternative to the declaration: `ThemeProvider` defaults to `"system"` and REMOVES a
`data-theme` it did not put there, so an app that declared only the attribute would paint its
palette and then flip out of it on mount — the failure is not a flash but a wrong palette,
which is worse.

## Consequences

- Three facts are duplicated outside the packages that own them: the storage key, the theme names,
  and which palettes are dark. That is the price of running before the bundle, and it is held
  rather than accepted — `tests/architecture/test_theme_bootstrap.py` checks each against its
  source (`theme.tsx`, `themes.ts`, `tokens.css`), so a sixth theme cannot ship without this file
  learning about it, and the two app copies are held byte-identical to each other.
- The script's load-bearing properties are all invisible in review, so they are pinned too: the
  same test refuses a `defer`, `async` or `type="module"` attribute on the tag, and refuses a tag
  that does not sit in the head ahead of the module entry point. A one-word edit that looks like a
  modernisation would otherwise bring the flash back with no other symptom.
- Existing apps take the fix through a template update, which overwrites the script (it is
  deliberately not in `_skip_if_exists` — it is framework-owned) and adds the tag to `index.html`.
  An app that has diverged in its document adds the two lines by hand.
- The framework still renders nothing on a server, and this ADR is the reason it does not need to
  for this purpose.

## Measurement

Probed against the example app's running dev server in Chromium with the module entry point
**blocked at the network layer**, so nothing React does can be mistaken for the pre-paint stamp:

| | `data-theme` | resolved `color-scheme` |
|---|---|---|
| without the bootstrap | absent | `normal` (the UA paints a white canvas) |
| with the bootstrap | `dark` | `dark` |

`terp.theme` was set to `"dark"` in `localStorage` and the browser's own preference to light, which
is the combination the media query cannot answer and the one every report of this came from.
